# Android ↔ Linux parity matrix

**Status: authoritative.** This file, not `Linux_QT_Client_Plan.md`, is the
acceptance checklist for parity work. The plan document predates several
locked decisions and still describes a dual-Qt/Ubuntu-Touch target; where the
two disagree, this file and `AGENTS.md` win.

The Android behaviour contract is `~/git/busnes.app/kypost-android/app/AGENTS.md`.
The wire contract is the backend Go source
(`~/git/busnes.app/kypost-server/backend/internal/api/`), never a guess.

## How to read a row

| Status | Meaning |
| --- | --- |
| **Matched** | Linux does the same thing, and a test pins it. |
| **Equivalent** | Different mechanism, same user-visible outcome. The mechanism is named. |
| **Missing** | Android has it, Linux does not, and it is agreed that Linux should. |
| **Intentional difference** | Android has it, Linux deliberately does not. A reason is required, not a shrug. |
| **Blocked** | Waiting on the backend or on a platform capability. |

A row may not sit at **Missing** without an owner phase. A row may not sit at
**Intentional difference** without a reason someone could argue with.

| Refresh before opening from a notification | Matched | Added 2026-08-22. `MailController::openFromNotification()` answers from the cache when the message is already there, and otherwise selects the Inbox, refreshes, and answers when that lands — so the common case (a push arrives up to 90 s before the sync that would fetch it) no longer opens a blank detail page. A **delta** refresh, not a forced full resync: the relay's cursor protocol returns everything after the stored cursor, and a message that has just arrived is by definition after it, so a full resync would re-download every body to learn the same thing. When the message still cannot be found — filed elsewhere by a server-side rule, or deleted from another client — the roots open nothing and `lastError` says why. |
| Per-route response size limits | Matched | Added 2026-08-22. `HttpClient` enforces a ceiling on both the declared `Content-Length` (at the headers, before any body arrives) and the running byte count (the only guard a chunked response leaves), reporting `NetworkError::ResponseTooLarge` and discarding the partial body. Shape follows Android's `MemoryBudget.kt`; **the inbox value differs**: Android's window is `bodies=0`, Linux's carries every body whole, because the PGP classification reads them. Default 8 MB (also older inbox pages, which carry no bodies: the relay measured 184 KiB per 500 such rows), inbox window 16 MB (was 64 MB for 500 rows; 50 rows of ordinary mail are ~1.3 MiB by the relay's 13.3 MiB per 500), attachment 25 MB. `RelayMailSourceTest::fetchOlderKeepsTheDefaultResponseCeiling`. |
| Inbox window size and older mail | Matched | Added 2026-10-17 (plan L12), after Android #183. The window is `GET /api/inbox?limit=50&mailbox=&since=` (`MailRepository::kInboxPageSize`; bodies still included, unlike Android's `bodies=0`). Scrolling a list to its end (`onAtYEndChanged`, both roots; not in search) asks `MailController::loadOlder()` for `GET /api/inbox?limit=50&mailbox=&before=<oldest held row>&bodies=0` (`serveInboxBefore`), one request at a time, never while locked. Once a page lands, its `nextBefore` is the oldest held row, so the next page starts there, and that survives a restart. Rows are stored with `metadata_only` (migration 011): the page has no body, attachment hint or PGP flags, so the reader treats them like a search hit, fetching the body on open from `GET /api/mail/body` into the cache. A page stops paging for that oldest row when `hasMore` is false, when it adds nothing, or when there is no `hasMore` at all: an old relay ignores `before=` and sends its window, which is not stored. A page is dropped if the account changed (`stillCurrent`) or the folder's oldest row moved while it was out; one for a folder no longer shown is stored but not painted. **Resync boundary** is by message number, which is what the relay pages by (IMAP UID, or the id after `n1:<generation>:`), not by date: a full window deletes absent rows at or above its oldest row and keeps those below, but only if some held row reaches the window. Otherwise the held rows are older than the window with possibly unseen mail in between, which paging (it starts at the oldest held row) would never fetch, so they are dropped as before L12. A window shorter than 50 rows is the whole folder. A delta with `hasMore` (more new mail than one window) applies the same reachability test to `nextBefore`. **Differs from Android:** Android tracks `inWindow` and walks the gap with up to 20 overflow pages; Linux drops the unreachable rows and lets paging refetch them. Older rows the relay later deletes stay cached until a window covers them again, as on Android. `MailPagingTest`, `MailControllerTest`, `tst_LoadOlder`. |
| Pull-to-refresh on mobile | Matched | Added 2026-10-11 (plan L8). Dragging the mobile list past its top and releasing runs the same `MailApp.refresh()` as the Refresh button and desktop Ctrl+R. An empty folder still shows the Refresh button, since its list is hidden. `tst_PullToRefresh` checks the gesture on a bare ListView with mouse drags. Not yet tried on a touch device. |
| Snooze | Matched | Added 2026-10-17 (plan L9). Android #214 (kypost-android@b2379e99): `POST /api/inbox/actions` `{action:"snooze", messageIds, mailbox, wakeAt}`, `wakeAt` whole-second UTC RFC 3339, strictly after now and at most 366 days ahead (`snooze.go:parseWakeAt`). Linux sends the same (`RelayMailSource::performAction`). Presets are Android's `WhenPicker.kt`, computed in `core/domain/Snooze.cpp` in the local zone: Later today (now + 3 h, down to the hour, hidden from 21:00), This evening (18:00, hidden within the hour), Tomorrow 08:00, Next week (next Monday 08:00); repeats dropped. Custom is a typed date and time, refused when unparseable, skipped by DST, or outside 1 minute to 365 days ahead (`SnoozeTest`); `MailController::snoozeEmails` refuses the same window before any request. **Differs from Android:** the custom time is two text fields, not a date and a time picker. Offered in the reader toolbar (both roots), the desktop list context menu and the mobile swipe-left panel next to Archive. Neither client hides it in Drafts, Sent or Trash. The Snoozed folder is a fixed entry at the end of both roots' folder list, matched by exact name: the relay gives it no special-use role (`adapters/imap/snooze.go`). In Snoozed, Snooze becomes Unsnooze, which is a `move` from Snoozed to INBOX (`unsnoozeEmails`); the relay drops the old wake record at the old wake time. Snoozed is never offered as a Move target: mail moved there has no wake time. Like Android's reader, there is no undo. |
| Scheduled send | Matched | Added 2026-10-17 (plan L10), after Android #215. Compose has **Send Later**: Android's presets (later today, three hours on the hour; this evening 18:00 if over an hour away; tomorrow 08:00; next Monday 08:00) or a typed date and time, five minutes to 365 days ahead (`core/domain/SendLater`). `sendAt` goes as whole-second UTC RFC 3339 on `POST /api/mail/send` and on `send-pgp`, and a 202 `{scheduled, sendAt}` is the success, only when asked for. Before either, `GET /api/scheduled` is asked: a relay without the route (404) ignores `sendAt` and would send at once, so nothing is sent. `MailController` refuses a time outside the relay's one-minute-to-366-day window before any request. A client-encrypted send stays end-to-end encrypted: every delivery is dated `sendAt` (`validateScheduledPGP`) and `draftCopy` is the same self-encrypted PGP/MIME draft Save Draft uploads (`buildEncryptedDraft`); if that copy cannot be made, nothing is sent. A scheduled plain send never offers the one-time-link re-send, which would go out at once. **Scheduled** (desktop header button, mobile drawer) lists `GET /api/scheduled` with each row's state and the relay's reason; a waiting one is cancelled with a confirming second tap (`POST /api/scheduled/{id}/cancel`), which returns it to Drafts (200) or queues that (202). Ids other than `[A-Za-z0-9-]{1,64}` are refused before a request. **Differs:** Android offers scheduling only on client-custody accounts; Linux offers it on any account whose Send works here, because the relay schedules plain mail itself. Android also caps scheduled attachments at 12 MB for its heap; Linux does not. |
| Unread counts on tabs and folders | Matched | Added 2026-10-17 (plan L13), after Android #189 (`feat/unread-counts`). Counts are cached rows whose `status` is exactly `unread`, so they cover only what this device has synced, never a server total. Folders: one grouped query, `EmailDao::unreadCounts` (`SELECT folder, COUNT(*) ... GROUP BY folder`), re-read on every change rather than adjusted (`MailController::recountUnread`), published as `MailApp.unreadCounts`. Shown as "Work · 3", the bare label at zero, no cap (`Format.withUnread`, `tst_UnreadLabel`). Recounted after a refresh, a folder switch, mark read/unread (and its rollback), a folder listing or folder mutation, and a successful archive, delete, spam, move or snooze, which now also removes the source copies from the cache; that removal is skipped if the pairing changed meanwhile (guard in `tests/guards.tsv`). | Multi-select and undo | **Missing** (L16) | Android: long-press selection with Archive, Move, Junk, Delete, Snooze and Mark read/unread, capped at 500 ids, one `/api/inbox/actions` call per source folder, rows keyed by (folder, id). ## 3. Pairing, credentials, recovery

| Capability | Status | Notes |
| --- | --- | --- |
| Pairing, TLS pinning, credential sealing, deregistration | Matched | The server-published `pin=` is honoured as of 2026-08-27. `parseNativePairLink` normalises it (`sha256/` prefix optional, base64 SHA-256 of the SPKI) and **refuses the link outright on a malformed value** rather than downgrading to TOFU, and `beginPair()` arms it *before* the registration POST, so the request carrying the pairing token and the push credentials is pinned rather than pinned-afterwards. A link with no `pin=` is still TOFU, which is what the relay publishes when it cannot read its own serving certificate. Matches Android's `NativePairingDeepLinkParser`. **Limit, accepted 2026-08-27:** background re-registration still suspends the stored pin and re-anchors to whatever key answers, so an attacker with a locally trusted CA has a window at every push-endpoint rotation. Enforcing it there would abort every relay request until the user ran "Reconnect to server" whenever the fronting proxy's key rotated — which for the documented `cloudflared` deployment the operator neither holds nor controls. Reason recorded at `DeviceRegistrationService::reregistrationParams()`; the real fix is server-side. |
| Non-destructive "Reconnect to server" | Matched | Added 2026-08-22, as `reconnectToServer()`. Note the review's premise was partly wrong: `removePairing()` never called `LocalDataWipe`, so cached mail and contacts already survived unpairing. What unpair actually costs is a server-side deregistration and a fresh pairing link. |
| Staged account replacement (register, then purge) | Matched | Added 2026-08-22. Pairing a **different** account now erases the previous one's cached data — and only after the replacement registration has succeeded, so a failed pairing cannot delete a working account's mail. If the purge leaves anything behind, the new pairing is refused and the device is wiped: no table carries a subscriber column, so survivors are readable by whoever pairs next. Mirrors Android's `PushSyncCoordinator.attemptPairing`. |
| Serialised registration / re-registration / pull | **Partial** | `reconnectToServer()` and `pairFromParsedParams()` guard on `m_inNetworkCall`, so no two registrations overlap, and the previous account is captured **before** the request rather than re-read after it (the TOCTOU Android's `registrationGate` closes by reading inside the mutex). Registration is still not *serialised* against an in-flight pull. As of 2026-08-22 it no longer needs to be for the mail and push paths, which discard a reply the current pairing did not authorise (row below) instead of blocking the request that produced it. Audited 2026-08-23 rather than assumed: every repository that writes account-scoped data through a DAO carries such a guard, and the two that carry none persist nothing. The audit found one site that did not — `PgpQrController` kept the previous account's key-exchange QR on screen, so a correspondent scanning it would have exchanged keys with the account this device had just removed.
